# Pangpangshop 架构设计 v1

## 1. 目标与边界

将现有“可运行的商店演示站”演进为可真实经营的库存预约站：商品和库存可管理，客户可提交预约，后台即时收到提醒，运营人员可主动联系客户并跟进预约。

当前版本不提供在线支付。支付仅作为未来可选扩展；数据库、邮件/通知和身份认证通过适配器接入，便于后续选择供应商。

## 2. 当前状态

已有：Next.js 前台、商品目录、分类、搜索、购物车交互、模拟订单、模拟联系表单、评论展示。

缺少：数据库、预约记录、库存预留、后台管理、运营提醒、邮件发送、SEO 基础文件、生产监控与自动化测试。

## 3. 目标架构

```text
浏览器
  │
  ├─ Next.js App Router
  │    ├─ 服务端页面：首页、分类、商品详情、SEO 元数据
  │    ├─ 客户端交互：购物车、筛选、收藏、预约表单
  │    └─ Route Handlers / Server Actions：受控业务入口
  │
  ├─ 应用服务层
  │    ├─ CatalogService      商品、分类、价格、库存读取
  │    ├─ CartService         匿名/登录购物车
  │    ├─ ReservationService  创建预约、库存预留、状态流转
  │    ├─ InventoryService    可售库存、预留与释放
  │    ├─ ReviewService       已购用户评价审核
  │    └─ ContactService      联系消息与客服工单
  │
  └─ 基础设施适配器
       ├─ MySQL（InnoDB）     业务数据与库存事务
       ├─ Object Storage/CDN  商品图片
       ├─ Notification        管理后台提醒与邮件通知
       ├─ Email Provider      预约确认与客服联系邮件
       ├─ Auth Provider       登录、会话、角色
       └─ Monitoring          错误、性能、审计日志
```

### 设计原则

- 页面优先使用 React Server Components；只把筛选、购物车和表单等需要浏览器状态的区域做成 Client Components。
- 不让页面直接读写数据库。所有写入经由应用服务层，并在服务端执行鉴权、价格重算和输入校验。
- 预约提交由服务端在事务内执行库存校验、库存预留和预约记录创建；不能信任客户端传来的价格或库存值。
- 每个预约都有到期时间；过期、取消或拒绝后必须释放已预留库存。
- 第三方服务只通过环境变量和 adapter 接入；密钥绝不进入浏览器包或 Git。

## 4. 建议目录结构

```text
src/
  app/                       # Next.js 框架入口
    (store)/                 # 前台路由：商店、分类、商品详情
    (account)/               # 可选登录与预约历史路由
    admin/                   # 管理后台路由，角色保护
    api/                     # 后端 HTTP 入口（Route Handlers）
  frontend/                  # 前端 UI 与浏览器状态
    components/              # 商店与后台组件
    context/                 # React 客户端状态
    assets/                  # 开发期前端素材
  backend/                   # 服务端业务边界
    services/                # 预约、库存、提醒业务服务
    repositories/            # MySQL 数据库读写
    adapters/                # 邮件、通知、存储、认证适配器
    validation/              # 请求与领域校验
  shared/                    # 前后端都可安全引用
    catalog/                 # 商品种子数据
    types/                   # TypeScript 类型
```

## 5. 核心数据模型

| 领域 | 最小实体 | 关键字段 |
|---|---|---|
| 商品 | Product、ProductVariant、Category、ProductImage | slug、标题、描述、上架状态、币种、售价、库存 SKU |
| 顾客 | User、Address、Session | 邮箱、角色、默认地址 |
| 购物 | Cart、CartItem | 顾客/匿名 token、商品变体、数量 |
| 预约 | Reservation、ReservationItem、ReservationContact | 预约号、预约数量、联系姓名、邮箱/电话/社媒、状态、到期时间 |
| 库存 | Inventory、InventoryReservation、InventoryAdjustment | 在库数、已预留数、可预约数、预留到期时间、变动原因 |
| 运营 | ContactMessage、Review、AdminNote | 处理状态、审核状态、客户沟通记录 |
| 审计 | AuditEvent、NotificationEvent | 事件类型、来源、去重 ID、发送和处理结果 |

### MySQL 数据库设计要求

- 使用 InnoDB 表引擎和 UTF-8 字符集；所有业务表使用外键或明确的关联索引。
- 每个预约提交在单个数据库事务中执行：锁定库存记录、验证可预约数、写入预约和预约商品项、增加预留数，再提交事务。
- 库存行以 `SELECT ... FOR UPDATE` 锁定，防止两个客户同时预约最后一件商品时发生超卖。
- `Inventory` 至少保存 `on_hand`（在库）、`reserved`（已预留）和 `available`（可预约，计算值）三个数量；可预约数必须由服务端计算。
- 为 `Reservation.status`、`Reservation.expires_at`、`Reservation.reference_no`、`ReservationContact.email` 以及各外键建立索引，以支持后台待办、过期释放和客户查询。
- 连接字符串只放在 `DATABASE_URL` 环境变量中，不提交 `.env.local`；数据库账户按最小权限创建，生产环境启用定时备份与恢复演练。

### 预约状态机

```text
submitted → notified → contacted → confirmed → fulfilled
     ├→ cancelled
     ├→ expired
     └→ declined
```

`submitted` 时先预留库存；`cancelled`、`expired`、`declined` 时释放库存。初始建议预约有效期设为 48 小时，并在后台做成可配置参数。

## 6. 关键业务流程

### 6.1 浏览与购物车

1. 服务端读取已上架商品、分类和图片。
2. 游客取得随机、HttpOnly 的购物车 token；登录后将游客购物车合并至用户购物车。
3. 每次更新购物车都重新校验变体是否可售、数量上限和当前库存。

### 6.2 预约与库存预留

1. 客户选择商品/数量后填写姓名、至少一种联系方式（邮箱、电话或社交账号）和备注。
2. 服务端校验库存、数量、联系信息和反垃圾规则。
3. 在一个数据库事务中创建 `submitted` 预约，锁定对应库存，并生成预约号。
4. 系统向后台发送“新预约”提醒，同时向客户发送已收到预约的确认信息。
5. 管理员在后台查看预约，记录联系结果，并切换为 `contacted`、`confirmed`、`declined` 或 `cancelled`。
6. 到期未处理的预约自动标记 `expired` 并释放库存；完成交付后标记 `fulfilled`。

### 6.3 管理后台

- 管理员登录后管理商品、库存、图片、预约状态、客户联系方式、内部备注、联系消息和评论审核。
- 所有后台写操作写入 `AuditEvent`；管理员权限在服务端校验。

## 7. 安全与可靠性

- 所有 API 和 Server Actions 使用 schema 校验、长度上限、类型检查与统一错误返回。
- 预约、登录、联系与评论接口设置限流和反垃圾机制。
- 客户联系方式属于个人信息：只在后台对授权人员显示，日志中遮罩，设置保留与删除策略。
- 管理路由使用角色访问控制；客户只能凭安全链接或登录后查看自己的预约。
- 生产环境启用 HTTPS、CSP、安全响应头、结构化日志、错误追踪和数据库备份。
- 在上线前补充隐私政策、退换货政策、配送政策、Cookie/分析声明和可访问的客服联系方式。

## 8. SEO 与性能

- 添加 `robots.ts`、`sitemap.ts`、`manifest.ts`、站点图标和商品/组织 JSON-LD。
- 为商品和分类页实现动态 `generateMetadata`，并提供 Open Graph 图片。
- 只保留 `public/` 中的生产图片，移除 `src/assets/images` 的重复副本。
- 使用 `next/image`、正确的 `sizes`、LCP 图片 `priority` 和压缩后的 WebP/AVIF 资源。
- 保持商品页可静态生成或按需再验证；购物车、账户与管理后台保持动态。

## 9. 开发阶段与验收标准

### 阶段 A：工程基线（第 1 周）

- 统一使用 npm，保留 `package-lock.json`，移除重复锁文件/无用依赖。
- 修正项目名称、README、Windows 兼容的 clean 脚本。
- 整理唯一应用目录为 `web/`，建立 `.env.example`、代码格式化、测试与 CI。
- 加入基础 SEO、错误页、加载态、空状态和无障碍检查。

验收：新电脑可通过 `npm ci && npm run build` 构建；Git 只提交一个应用目录；首页、分类页、商品页均可访问。

### 阶段 B：数据与后台（第 2–3 周）

- 建立 MySQL（InnoDB）schema、迁移、种子数据和 repository 层。
- 将内存数据替换为数据库；实现受保护的管理后台。
- 实现商品、图片、库存、预约状态、内部备注和联系消息的管理。

验收：重启服务后数据仍存在；管理员可上架商品、调整库存并查看预约。

### 阶段 C：预约流程与通知（第 4 周）

- 接入持久购物车、预约表单、预约号、库存预留与到期释放。
- 完成后台新预约提醒、客户确认通知、预约详情页和运营跟进备注。

验收：游客可完成预约；无法超卖；每条预约可追溯；后台能在一分钟内看到新预约提醒。

### 阶段 D：运营与履约（第 5 周）

- 完成批量预约处理、库存调整、导出、联系记录和发货/交付标记。
- 支付模块保留为未来功能，不纳入本期开发。

验收：管理员可完成从新预约到交付/取消的全流程，系统准确释放过期预约库存。

### 阶段 E：上线与增长（第 6 周）

- 生产部署、域名、环境变量、监控、备份、分析与 SEO 提交。
- 压测关键接口，完成浏览器端端到端测试、可访问性与移动端验收。

验收：生产环境监控正常、核心交易链路通过、性能和错误基线已记录。

## 10. 当前需要确认的产品决策

在进入阶段 B 前，需要确定：

1. 用户预约时必须填写哪些联系信息：邮箱、手机号、微信号或其他社交账号。
2. 预约库存的有效期（建议 48 小时）以及逾期处理规则。
3. 商品是否有真实库存、变体（材质/尺寸）和预售规则。
4. 你收到提醒的渠道：后台待办、邮件，或两者都需要。
5. 是否需要中文、英文或多语言。
6. 管理后台由哪些角色使用，以及是否需要多人协作审批。

## 11. 首个开发迭代

首个业务迭代实现“库存预约闭环”：数据库中的商品和库存、预约表单、库存预留、后台预约列表、管理员新预约提醒、联系记录和预约状态流转。支付适配器不在本期范围内，只保留未来扩展位置。
